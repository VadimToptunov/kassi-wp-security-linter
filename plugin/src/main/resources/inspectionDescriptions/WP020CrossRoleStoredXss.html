Reports a cross-role stored XSS chain: request data ($_GET, $_POST, $_REQUEST, $_COOKIE, REST parameters, selected $_SERVER[HTTP_*]) written to a storage sink (update_option, update_user_meta, update_post_meta, $wpdb->insert(), wp_insert_post()) and later read back through the matching getter and echoed on an admin page without an escaper. Strong when the writer runs on a public hook (wp_ajax_nopriv_*, REST permission_callback => __return_true) and the reader sits behind a capability check; weak when the writer and reader share a cap tier (self-XSS).

The real detector is plugin-wide and lives in the bounty-pipeline project (StoredXssCheck); the IDE keeps the rule registered for completeness.

Vulnerable

// public writer
add_action( 'wp_ajax_nopriv_p_save', 'p_save_html' );
function p_save_html() {
    update_option( 'p_html', $_POST['html'] );
}

// admin reader
function p_render_settings() {
    if ( ! current_user_can( 'manage_options' ) ) return;
    echo get_option( 'p_html' );
}

Fixed

function p_render_settings() {
    if ( ! current_user_can( 'manage_options' ) ) return;
    echo wp_kses_post( get_option( 'p_html' ) );
}

sanitize_text_field on the write side only strips tags; it keeps quotes, so a value echoed inside an HTML attribute can still break out (CVE-2024-11199 pattern). wp_kses, wp_kses_post, esc_html, esc_attr, esc_url on the read side are the safe choices.
